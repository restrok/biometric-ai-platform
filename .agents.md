# Engineering, Architecture & Autonomous Agent Guidelines

## 🎯 Core Engineering Philosophy: Radical Simplicity (KISS & YAGNI)

1. **Simplicity First (KISS):** Always favor simple, flat, and explicit code over clever abstractions, deep inheritance hierarchies, or premature design patterns. Code should be immediately obvious to another engineer.
2. **No Speculative Engineering (YAGNI):** Never build generic frameworks, dynamic dispatch layers, or configuration abstractions for hypothetical future use cases. Solve strictly the concrete problem requested.
3. **Minimal Dependencies:** Do not add third-party libraries for trivial operations that can be implemented cleanly with the Python 3.11 standard library (e.g., `math`, `statistics`, `urllib`, `dataclasses`, `pathlib`).
4. **Cohesive Modules:** Maintain cohesive, self-contained domain modules. Avoid over-fragmenting logic into micro-files or single-function files when a single clear module suffices.

## ⚡ Concurrent Agent Execution & Parallel Orchestration

When operating as or delegating to autonomous sub-agents in complex workflows, follow this parallelization protocol:

### When to Parallelize
- Spawn concurrent sub-agents or tasks whenever work items belong to isolated domains (e.g., feature implementation in one module while writing tests for another, or executing security/lint audits alongside documentation updates).

### Standard Sub-Agent Roles
1. **`qa-verifier`**: Executes `ruff`, `mypy`, and `pytest` on modified targets, resolving formatting, linting, and typing regressions.
2. **`security-auditor`**: Performs secret scanning (`gitleaks`), SAST checking (`ruff check --select S`), and dependency vulnerability audits (`pip-audit`).
3. **`test-writer`**: Formulates and updates isolated unit and regression test cases without mutating production business logic.

### Strict Disjoint File Rule
- Concurrent sub-agents **MUST** operate on strictly disjoint file sets (e.g., Agent A edits `src/storage/engine.py` while Agent B edits `tests/test_storage.py`). Never allow concurrent write operations on the same file to prevent race conditions, clobbered edits, and git merge conflicts.

## 🛡️ Core Quality & Platform Rules

### 1. Package & Dependency Management (Strict `uv`)
- Always use `uv` for dependency management (`uv add`, `uv run`, `uv sync`).
- **NEVER** use raw `pip install`. All dependencies must be version-locked in `pyproject.toml` and `uv.lock`.
- Tool commands must be run via `uv run` (or target `make` commands).

### 2. Typing & Static Analysis (Zero-Tolerance)
- All new functions, methods, and classes **MUST** include complete Python 3.11 type annotations (`typing`, `pydantic`). Untyped definitions fail CI/CD.
- Mypy executes with `check_untyped_defs = true`, `warn_unused_ignores = true`, and `warn_redundant_casts = true`.

### 3. Pre-flight Verification (`make check` / `make -j check`)
- Before completing any task, commit, or pull request, the complete verification suite MUST pass:
  ```bash
  make -j check
  ```
  This executes `lint` (Ruff & Mypy), `security` (pip-audit, Gitleaks, Ruff SAST `S`), and parallel `test` (Pytest-xdist + Coverage) with **zero errors**.

### 4. Git & Commit Message Standards (Conventional Commits)
- All commit messages must strictly follow Conventional Commits:
  - `feat:` New feature
  - `fix:` Bug fix
  - `chore:` Maintenance, dependency updates
  - `refactor:` Code restructuring without logic changes
  - `docs:` Documentation changes
  - `test:` Adding or modifying tests
  - `ci:` CI/CD pipeline or build tool modifications
  - `perf:` Performance improvements
- Direct pushes to `main` without passing checks are forbidden. Production releases are triggered by semantic tags (`v*.*.*`).

### 5. Architecture & Decoupling
- **Decouple Business Logic:** Keep physiological modeling, algorithms, and domain rules decoupled from FastAPI routers, external APIs, and cloud SDKs (GCP, BigQuery, Firestore, Garmin, Fitbit). Accept injected dependencies or pure data structures (`dataclass`, `BaseModel`, `dict`, `DataFrame`).

## 🚀 Pull Request & Code Review Standards

All AI agents and contributors must adhere to these standards when creating, documenting, or reviewing Pull Requests (e.g., via `gh pr create` or `gh pr review`):

### 1. PR Titles
- Must strictly follow Conventional Commits format: `<type>(<scope>): <imperative summary>`.
- Max 72 characters, lowercase type and summary, and **no trailing period**.
- Allowed types: `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `ci`, `perf`.

### 2. PR Descriptions
- Must strictly populate every section of `.github/pull_request_template.md`:
  - **Summary & Motivation (Why):** 1-3 sentences focusing on the concrete objective.
  - **Key Changes (What):** Bullet points of technical changes made.
  - **Verification (How it was tested):** Commands executed and explicit confirmation of `make check` results.
  - **Quality Checklist:** All boxes checked.
- Zero boilerplate or generic fluff—focus purely on technical facts and verifiable outputs.

### 3. PR Size & Scope
- Keep PRs small, atomic, and focused on a single concern.
- Never mix unrelated refactoring, cosmetic changes, or dependency upgrades with feature/fix work.

### 4. Code Review Comments (Conventional Comments)
When reviewing code or leaving review comments on PRs, prefix every comment with a standard label:
- `issue (blocking):` For bugs, regressions, security risks, or broken logic.
- `suggestion (non-blocking):` For KISS/simplification improvements, readability, or cleaner idioms.
- `question:` For inquiries or clarifications on design decisions and edge cases.
- `nitpick (non-blocking):` For minor naming, formatting, or documentation tweaks.
